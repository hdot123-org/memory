# 教训：过度设计验证陷阱

**日期**: 2026-08-05
**严重度**: 高（浪费多个 session 的调查时间）
**触发场景**: 修复 SessionEnd hook "超时" 问题

## 问题轨迹

```
真实问题（可能有）
  → 研究竞品架构（Grok sidecar）
  → 兴奋：这个架构很好！
  → 跳跃：采用竞品架构来解决
  → 合理化：为架构寻找理由（"JSONL 解析慢 2-5s"）
  → 缺失验证：从未实测原始假设
  → 用户追问 3 次才发现 16 行甚至 1 行都不需要
```

## 三层假前提

| 层级 | 假设 | 实测 | 耗时 |
|------|------|------|------|
| 1. 性能 | JSONL 解析 2-5s 导致超时 | 19MB 文件 0.14s | 0s |
| 2. 功能 | session_end_logger 停止工作 | 正常运行，写到其他项目目录 | 0s |
| 3. 架构 | 需要 sidecar 重构 | 不需要任何架构变更 | 0s |

## 根因

**没有先验证问题存在，就开始设计解决方案。**

具体失误：
1. 假设"JSONL 解析慢"从未被实测（实际 0.14s，40x margin）
2. 假设"session_end_logger 停止工作"只看了一个项目目录（实际多项目正常运行）
3. 从竞品研究直接跳到架构采纳，跳过了"最小修复是什么"这个关键问题

## 规则：验证优先于设计

**在提出任何解决方案之前，必须先回答：**

1. **问题是否真实存在？** — 用实测数据证明，不用推测
2. **最小修复是什么？** — 1 行能改的不用 10 行，10 行能改的不用架构重构
3. **当前方案是否在解决真实问题？** — 如果找不到问题证据，停止设计

## 检查清单

- [ ] 实测了原始假设（不是引用别人的说法）
- [ ] 检查了所有相关数据源（不是只看一个目录/文件）
- [ ] 提出了最小修复方案
- [ ] 验证了竞品架构是否真的需要（而不是"看起来很好"）

## 反模式

```
❌ 研究竞品 → 采纳竞品架构 → 为架构寻找问题
✅ 确认问题 → 实测根因 → 最小修复 → 验证
```
